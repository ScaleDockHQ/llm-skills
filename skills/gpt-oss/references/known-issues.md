# gpt-oss known issues

> Verified against vLLM recipes (GPT-OSS) troubleshooting and limitations, vLLM issues 35779, 38488 and 37030 and PR 28729 and 35907, llama.cpp guide #15396, Unsloth gpt-oss guide, OpenAI handle-raw-cot cookbook, 2026-10-11

| Symptom                                                                                                  | Cause                                                                                                       | Fix                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `openai_harmony.HarmonyError: error downloading or loading vocab file: failed to download or load vocab` | harmony fetches tiktoken files at runtime; offline or blocked network fails                                 | Download `o200k_base.tiktoken` and `cl100k_base.tiktoken` ahead of time, set `TIKTOKEN_ENCODINGS_BASE` to that directory (vLLM recipe)                                                                                                                                                   |
| `AssertionError: Sinks must be of type float32` on Blackwell                                             | Missing Blackwell env settings                                                                              | Follow the vLLM recipe's Blackwell section (`VLLM_USE_FLASHINFER_MOE_MXFP4_MXFP8=1` on compute capability 10.0)                                                                                                                                                                          |
| Garbage output on vLLM                                                                                   | `CUDA_HOME` unset, or CUDA below 12.8, or different CUDA for install and serve                              | CUDA 12.8 or newer, same version for install and serving (recipe, older install path)                                                                                                                                                                                                    |
| `torch::nvtoolsext` / `CUDA::nvToolsExt` link error                                                      | PyTorch without `+cu128` suffix                                                                             | Use a `+cu128` PyTorch build (recipe)                                                                                                                                                                                                                                                    |
| Triton `tl.language` not defined                                                                         | A second Triton (for example `pytorch-triton`) in the environment                                           | Keep only one Triton                                                                                                                                                                                                                                                                     |
| CUDA OOM on one H100 with defaults                                                                       | Default memory utilization and batched tokens too high for TP1                                              | `--gpu-memory-utilization 0.95 --max-num-batched-tokens 1024`; at TP2 keep below 0.95                                                                                                                                                                                                    |
| `content: null` or garbage first token on DGX Spark (SM121)                                              | vLLM CUTLASS FP4 path ([vllm#37030](https://github.com/vllm-project/vllm/issues/37030), open on 2026-10-11) | Community fix: Marlin MXFP4 backend and `TRITON_ATTN`; see `platforms-and-quants.md` (unverified for your build)                                                                                                                                                                         |
| Model "forgets" its reasoning between turns                                                              | By design: prior-turn `analysis` is dropped after a `final` message (vLLM issue 35779 closed as per spec)   | Put facts the model must keep in `content`, not only in reasoning. Do not "fix" by replaying old CoT                                                                                                                                                                                     |
| Tool loops degrade, repeated calls, or wrong tool after several steps                                    | Client drops the reasoning of the in-flight tool call, or sends it under the wrong field                    | Return the assistant's `reasoning` with its tool calls on the next request. vLLM reads `reasoning`; issue 38488 reports `reasoning_content` is ignored on input (LiteLLM and Vercel AI SDK style clients send it); fix is in progress upstream per that thread. Check the engine version |
| Reasoning text appears inline in `content` (`analysis...assistantfinal`)                                 | No reasoning parser, or an engine that does not split harmony output (TensorRT-LLM guide sample)            | vLLM `--reasoning-parser openai_gptoss`, SGLang `--reasoning-parser gpt-oss`, llama.cpp `--jinja` with default `--reasoning-format`                                                                                                                                                      |
| llama.cpp ignores top-level `reasoning_effort`, always medium                                            | llama-server reads only `chat_template_kwargs.reasoning_effort` (2025 guide comment)                        | Set `--chat-template-kwargs '{"reasoning_effort":"high"}'` server-side or send `chat_template_kwargs` per request                                                                                                                                                                        |
| Slightly odd or repetitive output on llama.cpp                                                           | Client or server defaults (`top-k 40`, `min-p 0.1`, repetition penalty)                                     | `--temp 1.0 --top-p 1.0`, disable repetition penalties, consider `min-p 0.01`                                                                                                                                                                                                            |
| Mangled tool arguments, extra newlines, tool-call thoughts tagged `final`                                | Third-party jinja templates differ from harmony (Unsloth compared them)                                     | Use the repo's current `chat_template.jinja` or the GGUF's embedded template; Unsloth says some fixes went upstream                                                                                                                                                                      |
| `content: ""` with only reasoning when `max_tokens` is low                                               | CoT consumed the budget at `high` effort                                                                    | Raise `max_tokens`, lower effort                                                                                                                                                                                                                                                         |
| Responses API on vLLM: usage counts zero, no annotations, tool events batched in streaming               | Documented vLLM limitations                                                                                 | Do not rely on usage accounting; prefer Chat Completions for function calling when streaming (matrix: function calling with streaming is unsupported on Responses)                                                                                                                       |
| Float16 GPUs (T4) overflow or give infinities                                                            | Trained in BF16; MXFP4 is emulated (upcast to BF16) on Ampere and older                                     | Use BF16 where available (Unsloth notes)                                                                                                                                                                                                                                                 |
| Safeguard model gives chatty or off-policy answers                                                       | Used as a general chat model                                                                                | Use it only for policy classification: policy in the developer message, content in the user message                                                                                                                                                                                      |

Other facts to keep in mind:

- vLLM `/v1/completions` applies no template; you must render harmony yourself.
- vLLM function calling supports only `tool_choice="auto"`.
- Raw CoT is not safety-trained to final-channel standards; strip it before showing output.
- `--reasoning-parser` may be redundant on recent vLLM, but passing it is harmless; verify with a request that returns
  both `reasoning` and `content`.
