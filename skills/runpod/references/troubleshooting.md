# Runpod troubleshooting

> Verified against runpod-workers/worker-vllm v2.29.0 README troubleshooting table, docs.runpod.io pods/connect-to-a-pod, serverless/load-balancing/overview, serverless/endpoints/send-requests, runpodctl v2.15.0 README (error codes), 2026-10-11

Start with logs: `runpodctl pod logs <pod-id> --tail 200`, `runpodctl serverless logs <endpoint-id> [--worker <worker-id>]`, and `runpodctl serverless health <endpoint-id>`.

| Symptom                                                   | Likely cause                                                                                  | Fix                                                                                                          |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `401 Unauthorized` on `api.runpod.ai`                     | Missing, wrong, revoked or under-scoped API key                                               | Re-export the key from its `0600` file; check a Restricted key has access to this endpoint                   |
| `401` from `*.proxy.runpod.net`                           | vLLM `--api-key` set and client sent another key                                              | Send the vLLM key, not the Runpod key                                                                        |
| `404 Not Found`                                           | Wrong endpoint id or path                                                                     | Base must end in `/openai/v1` for worker-vllm; check `runpodctl serverless list`                             |
| Connection refused or timeout                             | Endpoint not ready; workers still starting or scaled to zero                                  | Wait, poll `/health`, raise client timeout, retry                                                            |
| `Invalid model` / model not found                         | `model` does not match the served name                                                        | `GET /openai/v1/models`; set `OPENAI_SERVED_MODEL_NAME_OVERRIDE`                                             |
| Job returns `startup_error`                               | Out of memory, gated model without `HF_TOKEN`, or `MAX_MODEL_LEN` too large                   | Read the JSON error. Add `HF_TOKEN`, lower `MAX_MODEL_LEN` or `GPU_MEMORY_UTILIZATION`, or pick a bigger GPU |
| Workers stay `initializing`, never `ready`                | Model download slow, wrong `MODEL_NAME`, or crash loop                                        | Check worker logs; use cached models; confirm the Hugging Face repo name                                     |
| Queue grows, no workers start                             | `max workers` reached or GPU out of stock                                                     | Raise `--workers-max`, add alternative GPU types, check `runpodctl gpu list`                                 |
| Endpoint worked last week, now idle and failing           | Auto scale-down dropped `max workers` to 0 after 7 idle days                                  | `runpodctl serverless update <id> --workers-max <n>`                                                         |
| `429 Too Many Requests`                                   | Per-endpoint rate limit (for example `/run` 1000 per 10 s)                                    | Backoff with jitter, add workers, use `/openai/*` for chat traffic                                           |
| Job `TIMED_OUT` or cut at 600 s                           | Execution timeout default                                                                     | Raise it in endpoint settings, or reduce `max_tokens`, or stream                                             |
| Result gone from `/status`                                | Retention: 30 min after `/run`, 1 min after `/runsync`                                        | Poll sooner; store results yourself                                                                          |
| LB endpoint `no workers available`                        | Cold start; no worker ready                                                                   | Retry for up to a few minutes; set one active worker                                                         |
| LB endpoint `502`, worker alive about 8 minutes           | `PORT` or `PORT_HEALTH` does not match the app port or health path                            | Match `PORT` to the listening port; `/ping` must return 200 or 204                                           |
| LB `/ping` stays `204`                                    | Server still loading the model                                                                | Wait; confirm startup logs end with "Application startup complete"                                           |
| Pod proxy `502`                                           | App not running, no GPU attached, or server bound to `127.0.0.1`                              | Check Pod logs, bind `--host 0.0.0.0`, wait for model load                                                   |
| `/health` or `/metrics` open without a key                | `--api-key` only protects `/v1`, `/v2`, `/inference`                                          | Put the Pod behind your gateway; do not expose metrics publicly                                              |
| `runpodctl`: `no_credentials`                             | No `RUNPOD_API_KEY` and no config file                                                        | Export the key or run `runpodctl doctor`                                                                     |
| `runpodctl`: `unauthorized`                               | Bad or revoked key                                                                            | Create a new key, update the file                                                                            |
| `runpodctl`: `wait_timeout`                               | Pod did not reach running before `--wait-timeout`                                             | The Pod still bills. Read the `id` in the error, check logs, delete if stuck                                 |
| `runpodctl`: `usage_error`                                | Wrong flags                                                                                   | `--help` on the subcommand                                                                                   |
| Cannot create Pod: insufficient credit                    | Balance below one hour of the chosen GPU                                                      | Add credits                                                                                                  |
| Pods stopped or terminated unexpectedly                   | Balance reached $0                                                                            | Add credits; Pods without a network volume were terminated and lost disk data                                |
| Cannot attach network volume                              | Volume is in another data center, or Pod is Community Cloud, or attach attempted after deploy | Deploy in the volume's data center on Secure Cloud and attach at creation                                    |
| REST v1 or GraphQL script failing after November 15, 2026 | v1 retired                                                                                    | Migrate to REST API v2 (`/runpod:migrate` from the Runpod plugin)                                            |
| Docs or CLI text says "RunPod"                            | Old spelling                                                                                  | Write "Runpod"                                                                                               |

## When logs say nothing

1. `runpodctl serverless health <id>` for worker counts and queue depth.
2. Re-run with a tiny request (`max_tokens: 8`) and a smaller model to separate platform from model issues.
3. Check the Runpod status page and the console for incidents.
4. Collect endpoint id, worker id, time (UTC) and the error JSON before contacting Runpod support. Never include the API key.
